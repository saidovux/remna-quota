# Учёт трафика и синхронизация

У каждой части свой пользователь Remnawave, UUID подключений и счётчик. remna-quota не пропускает VPN-трафик через себя: измерения поступают от нод через панель. Сервис хранит наблюдаемый расход в своей PostgreSQL и рассчитывает остаток независимо для каждой части.

## Пакет без сброса

Для `NO_RESET` логический used_bytes увеличивается на разницу накопительного `lifetimeUsedTrafficBytes` панели. Сброс текущего счётчика не пополняет пакет. Повтор чтения того же снимка ничего не прибавляет. Необъяснимое уменьшение накопительного счётчика или устаревшая эпоха сброса дают ошибку учёта; прежние списания сохраняются. При обновлении старой базы первый накопительный снимок становится опорной точкой без пересчёта уже списанного расхода.

Если прежних наблюдений вообще нет, первый снимок управляемого пользователя учитывает весь его накопительный расход. Это закрывает случай, когда создание в панели завершилось, ответ потерялся, а текущий счётчик успел сброситься до следующей попытки. Старые записи с уже сохранённым расходом сохраняют прежние списания.

Нативный лимит рассчитывается так:

```text
остаток = max(0, логический лимит − учтённый расход)
списано до текущего счётчика = max(0, учтённый расход − текущий счётчик панели)
лимит панели = max(1, логический лимит − списано до текущего счётчика)
```

Например, из 70 GiB уже учтено 37. В панели сбросили счётчик, затем он показал 5. Логический расход теперь 42, остаток 28. Нативный лимит становится 33: при текущих 5 доступны ещё 28 GiB. В API логический лимит остаётся 70.

Если остаток нулевой, пользователь отключается в панели. Нативный лимит не опускается до нуля: ноль означал бы безлимит. MAIN при этом сохраняет свои настройки и доступ. При увеличении логического лимита с 70 до 100 после расхода 70 снова доступны 30 GiB.

Отключение пользователя запрещает новые подключения, но исходная Xray 26.7.28 не завершает открытые потоки VLESS при `RemoveUser`. В этой версии ноды `connections/drop` также не даёт точной изоляции: он ищет IP пользователя и уничтожает сокеты по IP, требуя `NET_ADMIN`. За обратным прокси это может не найти нужное соединение или затронуть другие сессии. Автоматически вызывать такой маршрут для квот сервис не должен. remna-quota работает через стандартный API Remnawave и не требует модифицированного Xray. Немедленное закрытие уже открытых потоков на такой конфигурации не гарантируется; удаление CDN из общей ссылки само по себе тоже не закрывает ранее импортированные подключения.

Перерасход не повышает лимит. Если пакет 50 MB израсходовал 76,94 MB до применения отключения, лимит панели остаётся 50 MB, учтённый расход остаётся 76,94 MB, остаток равен нулю. Повторная синхронизация и перезапуск не дают новую квоту. Коррекция старого ошибочно повышенного нативного лимита также не меняет расход и не включает пользователя.

Повтор PUT, продление срока и перезапуск не обнуляют расход. При удалении принадлежащего сервису пользователя панельная запись восстанавливается с остатком квоты; VPN-ключи при пересоздании могут измениться. Для нового независимого пакета можно создать отдельный аккаунт. Управляемого ручного сброса пакета в API сейчас нет.

## Периодические лимиты

Для DAY, WEEK, MONTH, MONTH_ROLLING границы периода и сброс определяет Remnawave. used_bytes соответствует текущему периоду панели, а observed_total_bytes накапливает наблюдаемые значения между сбросами. Синхронизация восстанавливает доступ после сброса, если часть включена и срок не закончился.

При переходе с NO_RESET на периодическую стратегию расход пакета начинает трактоваться как счётчик текущего периода. Это изменение правил квоты, а не обычное продление. Не переключайте стратегию при каждом повторе выдачи.

## Кто задаёт параметры

remna-quota хранит желаемые лимиты, сроки, состояние и профиль сквадов; Remnawave предоставляет измерения и исполняет ограничения. Ручная смена настроек управляемого пользователя в панели будет перезаписана следующим sync. Сервис изменяет только записи с точным description-маркером `remna-quota:<account-id>:<part-key>`.

После успешной синхронизации следующая назначается через `BACKEND_SYNC_INTERVAL` (по умолчанию 10 секунд). Диспетчер проверяет очередь раз в секунду и обрабатывает до четырёх аккаунтов одновременно. Медленный аккаунт занимает один слот; завершения остальных ждать не нужно. Ошибки откладывают следующий запуск с растущей задержкой до пяти минут и небольшим случайным разбросом. Более длинный `Retry-After` панели имеет приоритет. Расписание и число ошибок сохраняются в БД и переживают перезапуск.

Новые настройки сохраняются сразу и запускают обработку при наличии свободного слота; `Retry-After` сохраняет силу. HTTP-запрос ждёт до пяти секунд, затем получает `202`. Отмена запроса не отменяет сохранённое задание. `POST .../sync` может принудительно повторить обычную ошибку, но также соблюдает `Retry-After`. GET refresh только сохраняет наблюдения.

Сетевые вызовы выполняются вне транзакций PostgreSQL. Отдельная advisory-блокировка сериализует работу с одним аккаунтом между репликами; изменения желаемых настроек и чтение списка не ждут панели. Наблюдения сохраняются по частям. Перед подтверждением проверяется revision: старый ответ не подтверждает новые настройки. Общая ссылка при неподтверждённом состоянии возвращает `503`.

`observed_at` — время последнего принятого снимка, `applied_revision` — последняя подтверждённая версия настроек, `accounting_status` — `unknown`, `ok` или `anomaly`. При аномалии прежние счётчики сохраняются; ошибка не пополняет пакет. `next_retry_at`, `last_attempt_at`, `failure_count` описывают состояние повторов аккаунта. `synced_at` сохранён для совместимости.

Диагностика доступна через защищённые `/api/v1/diagnostics` (JSON) и `/api/v1/metrics` (Prometheus). Счётчики вызовов, ошибок и суммарной длительности относятся к текущему процессу; ожидающие изменения, ошибки учёта и возраст наблюдений вычисляются из БД. Отсутствующие снимки учитываются отдельно. Эти маршруты не опрашивают Remnawave.

## Пределы точности

- На всех нодах профиля с ограничением нужен положительный `consumptionMultiplier`. При нуле Remnawave умножает расход пользователя на ноль: наличие подключений и лимита в API не означает, что квота списывается. Это настройка всей ноды, не отдельного пользователя. Для безлимита конкретной части используйте `limit_bytes: 0`, сохраняя учёт на ноде. Если общая нода уже использует нулевой коэффициент для других клиентов, переход требует отдельной ноды или согласованного изменения их правил.
- Счётчики — снимки, а не журнал каждого пакета. Накопительный счётчик позволяет учесть трафик между сбросами, пока запись пользователя и сам накопительный счётчик сохранены. Трафик удалённого пользователя, который не был прочитан до удаления, восстановить из новой записи нельзя.
- observed_total_bytes — накопленный наблюдаемый расход с начала учёта, не гарантированная пожизненная статистика панели.
- Удаление/откат базы remna-quota теряет часть истории. Нужны резервные копии собственной базы.
- После внешнего сброса возможен промежуток до следующего успешного sync, когда нативный лимит ещё не пересчитан. Не сбрасывайте управляемые NO_RESET-счётчики вручную в обычной работе.
- Остановка трафика и уже открытых соединений зависит от Remnawave, обновления счётчиков и конфигурации нод. До выпуска пользователям требуется проверка реальным VPN-клиентом.
- В Remnawave 3.4.3 установленной версии сбор пользовательского расхода запланирован раз в 15 секунд, проверка превышения — cron `*/45` (на 0-й и 45-й секундах каждой минуты). Между измерением, записью статистики и применением отключения возможен перерасход. `BACKEND_SYNC_INTERVAL` не ускоряет измерения Remnawave. Маленькая квота не является точным ограничителем переданного количества байт; нельзя обещать остановку ровно на последнем байте.
- При недоступной панели сохраняются прежние показатели с stale/error; они не выдаются за свежий ноль. Уже применённые нативные лимиты не требуют доступности remna-quota.
