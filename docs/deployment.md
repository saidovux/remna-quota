# Развёртывание remna-quota

Основной режим создаёт пользователей Remnawave, синхронизирует квоты и выдаёт объединённые подписки. `BACKEND_ENABLE_MANAGED_ACCOUNTS=true` включён по умолчанию. Для отдельного сценария объединения существующих записей без управления ими есть [установка только для чтения](deployment-aggregation.md).

## Настроить Remnawave

Нужна Remnawave v3 с API пользователей и `GET /api/subscriptions/connection-keys/{id}`. Результаты проверки установленной Remnawave 3.4.3 приведены в [отчёте обследования](live-assessment-2026-09-23.md); другую версию проверяйте перед подключением.

1. Подготовьте внутренний сквад MAIN с обычными нодами и CDN со своими нодами/инбаундами. UUID этих сквадов задаются в `REMNAWAVE_PROFILES_JSON`.
2. Создайте отдельный серверный API-токен. Для работы и диагностики нужны scopes: `system:metadata`, `internal-squads:list`, `users:by-id`, `users:by-username`, `users:create`, `users:update`, `users:enable`, `users:disable`, `subscriptions:connection-keys`. Обычный сервис не удаляет пользователей и не вызывает сброс трафика. Существующий ключ сайта может иметь другой набор прав.
3. Укажите адрес панели и токен. HTTPS обязателен по умолчанию. Для доверенной Docker-сети доступны `REMNAWAVE_ALLOW_HTTP=true` и, если требует прокси панели, `REMNAWAVE_FORWARDED_FOR`, `REMNAWAVE_FORWARDED_PROTO`, `REMNAWAVE_CADDY_API_KEY`.
4. Не назначайте новым пользователям посторонние сквады вручную: сервис восстанавливает набор сквадов профиля. Не меняйте поле description с маркером `remna-quota:<account-id>:<part-key>`: оно защищает от присвоения чужого пользователя.
5. Для профилей с квотой проверьте `consumptionMultiplier` каждой ноды: обычный учёт требует `1`, нулевой коэффициент исключает списания. Безлимит задаётся пользователю через `limit_bytes: 0`. Не меняйте коэффициент общей ноды без проверки влияния на существующие подписки. Подключение пользователя при нулевом расходе само по себе не доказывает корректный учёт.

Две записи пользователя обеспечивают отдельные учётные данные и нативные счётчики даже при общей инфраструктуре. Выбор сквадов определяет, какие подключения относятся к MAIN/CDN. Связанные ограничения устройств/HWID пока не настраиваются через этот API; лимит устройств на весь объединённый аккаунт нельзя корректно получить простым удвоением настройки панели.

## Docker Compose

```bash
cp .env.example .env
chmod 600 .env
# Два независимых вызова; результаты сохранить в соответствующие поля .env:
go run ./cmd/quota-api keygen   # BACKEND_API_KEY
go run ./cmd/quota-api keygen   # QUOTA_DB_PASSWORD
```

Заполните:

```dotenv
BACKEND_PROVIDER=remnawave
BACKEND_ENABLE_MANAGED_ACCOUNTS=true
BACKEND_SYNC_INTERVAL=10s
BACKEND_PUBLIC_URL=https://subscriptions.your-domain.example
BACKEND_API_KEY=
QUOTA_DB_PASSWORD=
REMNAWAVE_BASE_URL=https://your-panel.example
REMNAWAVE_API_TOKEN=
REMNAWAVE_PROFILES_JSON={"main":["<main-squad-uuid>"],"cdn":["<cdn-squad-uuid>"]}
```

В `.env` допустимы одинарные кавычки вокруг JSON, как в примере корня. Compose сам формирует `BACKEND_DATABASE_URL` для своей базы и включает `BACKEND_PROVIDER=remnawave`. Пароль в этой Compose-строке должен быть безопасен для URL: генератор выдаёт подходящий алфавит.

```bash
docker compose config --services
docker compose build
docker compose run --rm --no-deps quota-api check-config
docker compose run --rm --no-deps quota-api check-provider
docker compose up -d
curl --fail http://127.0.0.1:8090/readyz
```

Если Go на сервере отсутствует, сгенерируйте два разных ключа командой `openssl rand -hex 32` и заполните пустые поля до запуска Compose. Можно использовать и другой криптографический генератор 32 случайных байт с URL-safe кодированием. Сборка образа не требует доступа к панели.

Сервис опубликован только на `127.0.0.1:8090`. PostgreSQL не имеет порта на хосте, хранит данные в отдельном томе `quota-api-postgres` и не подключается к базам Remnawave/Bedolaga. Миграции применяются при старте. `readyz` проверяет хранилище; состояние удалённых подписок проверяется по `sync_status` аккаунтов.

`check-provider` выполняет только GET-запросы к панели: читает версию и сквады, проверяет заданные профили и доступность чтения пользователей/connection keys на пробных несуществующих ID. База не открывается, пользователи не создаются. Команда использует обычную конфигурацию, поэтому синтаксически корректные `BACKEND_DATABASE_URL` и `BACKEND_API_KEY` всё равно обязательны. Без Docker: `go run ./cmd/quota-api check-provider`.

JSON-отчёт содержит `read_checks_passed`, `version`, `checks` и `write_scopes_verified: false`. Код завершения `1` означает неуспешную проверку; `missing_api_scope` соответствует HTTP 403, `invalid_api_token` — HTTP 401. Для пробных пользователей ответ 404 считается допустимым, поэтому результат не подтверждает права записи, выдачу реальных подключений или применение квоты на ноде. HTTP 403 также может быть вызван прокси; проверяйте scope и настройки доступа вместе. Ошибки прав при синхронизации части доступны как `last_error: "provider_access_denied"`.

Для запуска без Docker задайте `BACKEND_DATABASE_URL=postgres://...` на отдельную PostgreSQL и запустите `quota-api`. Нельзя направлять DSN в базу панели или бота. Перед подключением по публичной сети настройте проверяемый TLS PostgreSQL (`sslmode=verify-full` и доверенный сертификат).

## HTTPS и приложения

Создайте DNS-запись домена подписок на сервер и настройте HTTPS reverse proxy на `127.0.0.1:8090`. Сайт, бот и другие приложения обращаются к тому же API. Пример для существующего Nginx внутри TLS server block:

```nginx
location /sub/ {
    access_log off;
    proxy_pass http://127.0.0.1:8090;
    proxy_read_timeout 120s;
    proxy_cache off;
}
location / {
    return 404;
}
```

Пример публикует только общую подписку. Сайт обращается к `/api/v1/...` по внутренней сети или отдельному защищённому HTTPS-маршруту с Bearer-ключом. Если сайт работает в контейнере, `127.0.0.1` внутри контейнера — сам контейнер: подключите его к сети сервиса через Compose override и используйте `http://quota-api:8090`, либо организуйте защищённый маршрут через хост. Для больших нагрузок задайте ограничения частоты запросов на прокси; каждая загрузка подписки читает актуальные состояния из панели.

Не включайте кэш CDN для `/sub/*` и `/api/*`. Не записывайте URL подписок в access logs/аналитику: токен находится в пути. Заголовки приложения запрещают кэширование, но настройки внешнего прокси тоже должны это учитывать.

## Проверка перед выдачей пользователям

1. Создать отдельный тестовый аккаунт через API. В панели убедиться, что появились `<username>_main` и `<username>_cdn`, с разными данными подключения и правильными сквадами.
2. Импортировать общую ссылку в выбранный клиент, проверить подключения обоих типов и метки MAIN/CDN.
3. Задать CDN небольшой лимит и реально израсходовать его. Проверить отказ CDN в том числе по ранее скачанной конфигурации; MAIN должен работать.
4. Проверить расход/остаток обеих частей через `?refresh=true`, общий статус и список `/api/v1/accounts`.
5. Проверить отключение части, всего аккаунта, продление, увеличение лимита, нативный сброс и восстановление после недоступности панели.
6. Перезапустить сервис, убедиться в сохранении ID пользователей и общей ссылки; после смены токена старый URL должен возвращать 404.

Нативное применение квоты и завершение уже открытых соединений зависят от панели, настроек нод и её интервалов обновления. Локальные тесты не подтверждают эти свойства реального сервера.

Для NO_RESET учтённый расход хранится в собственной базе, а нативный лимит может отличаться от логического после внешнего сброса счётчика. Правила и пределы точности описаны в [учёте трафика](traffic-accounting.md). При обновлении с версии, где managed API был выключен, проверьте сохранённые accounts и профили перед включением фоновой записи в панель. Явное `BACKEND_ENABLE_MANAGED_ACCOUNTS=false` сохраняет режим только для чтения.

## Резервная копия и обновление

```bash
docker compose exec -T quota-postgres pg_dump -U quota -d quota -Fc > quota-backup.dump
```

Файл содержит секретные ссылки; храните его с ограниченным доступом. Перед обновлением создайте резервную копию. Не выполняйте `docker compose down -v`, если данные нужно сохранить. Для восстановления сначала остановите `quota-api`, восстановите дамп в отдельную проверенную базу, затем запустите сервис. Общие ссылки сохраняются только вместе с базой.

Обновление надёжности добавляет миграцию `00005_sync_schedule.sql`: колонку расписания и индекс. Накопленные списания, ID и токены не переписываются. Остановите все старые экземпляры обработчика до запуска новой версии; смешанный запуск старой и новой схемы блокировок не поддерживается. После резервной копии запустите новую версию, дождитесь миграции и подтверждения `applied_revision == revision` у частей. Старые записи попадают в очередь немедленно; до подтверждения общая ссылка может временно возвращать `503`. При откате остановите новые обработчики и восстановите проверенную резервную копию вместе со старой версией.

Каждый экземпляр использует до 12 соединений основного пула и до 4 отдельных соединений для блокировок операций. Учитывайте это при выборе `max_connections` PostgreSQL. На время сетевых запросов SQL-транзакции не удерживаются. Для мониторинга доступны `/api/v1/diagnostics` и `/api/v1/metrics` с Bearer-ключом; публиковать их без защиты не требуется.

## Переход со старого контроллера

Прежняя схема — один пользователь с несколькими пулами и зависимостью от Bedolaga. Новая — отдельные пользователи в одной API-модели. Старый код сохранён в `cmd/remna-quota`, настройки — `.env.legacy.example`, Compose — `compose.legacy.yaml`.

Автоматической миграции существующих оплат, пользователей и конфигураций пока нет. При подключении сервера нужно сопоставить ID сайта/бота, действующие сроки, использованный трафик и старые ссылки, затем выбрать перенос. Новые пользователи создаются с явными метками принадлежности; чужое совпадающее имя вызывает конфликт и не изменяется.
