# Обследование панели и сайта: 22–23 сентября 2026

**Исторический снимок до обновления multi-subscriptions.** Текущая модель сайта повторно проверена в [новом отчёте](site-review-2026-09-23.md). Основной API remna-quota теперь объединяет существующие подписки; описанный ниже API создания пользователей сохранён как необязательный режим.

## Вывод

Remnawave 3.4.3 поддерживает нужную схему. Проверка нового `quota-api` на действующей панели прошла: два отдельных пользователя, общая подписка, независимое отключение CDN, обновление его лимита и срока. Основное препятствие для подключения — текущая модель сайта: она хранит одного пользователя панели и одну подписку на клиента, а обработчик выдачи заменяет параметры этого пользователя.

Изменения `remna-quota` находятся в локальном проекте. Рабочий сайт ещё использует прежнюю интеграцию; постоянный `quota-api` на серверах не развёрнут. Платежи и цены остаются ответственностью сайта.

## Почему сайт пока не показывает две независимые подписки

Обследован активный код `/opt/site/backend`, а не архивные релизы. Для анализа локально сохранена выборка исходников в исключённый из Git каталог `tmp/site-baseline`; это не полная резервная копия сервера.

| Файл сайта | Текущее поведение | Изменение для подключения |
| --- | --- | --- |
| `internal/database/schema.sql` | Один `remnawave_user_id` у клиента; `subscriptions` имеет `UNIQUE(customer_id)` | Хранить отдельно права каждой части; использовать стабильный customer ID как ID объединённого аккаунта |
| `internal/remnawave/client.go` | DIRECT/CDN выбирает один сквад для одного пользователя; обновление сбрасывает его трафик | Передать выдачу двух пользователей `quota-api`; повтор задания не должен сбрасывать расход |
| `internal/provisioning/service.go` | Одно задание обновляет единственную подписку | Обновлять права нужной части и отправлять полную актуальную конфигурацию обеих частей |
| `internal/dashboard/service.go` | Один расход, лимит и URL | Возвращать общую ссылку и массив `parts` с отдельными показателями |
| `internal/httpapi/subscription_access.go` и `internal/subaccess/session.go` | Вход по нативному `/{shortUuid}` с сессией, привязанной к одному пользователю панели | Добавить вход по `/sub/{token}` через серверный resolver; сохранить обработку старых ссылок |

Особенно важен worker: нынешняя операция обновления вызывает сброс трафика даже при повторной обработке. Простая замена адреса API не решает ни независимость частей, ни корректность повторных заданий. При нескольких одновременных заданиях сайт должен сериализовать изменение прав одного клиента: `PUT` передаёт полное желаемое состояние и не объединяет конкурентные настройки автоматически.

Существующие 39 пользователей панели не связаны с двумя клиентами сайта. Их нельзя автоматически присвоить новым аккаунтам по похожему имени. Текущий адаптер требует точный маркер `remna-quota:<account-id>:<part-key>` и отказывается менять чужую запись.

## Проверка ключей и адаптера

Ключ выдачи сайта умеет читать, создавать и обновлять пользователей, но не имеет `subscriptions:connection-keys`, `users:enable`, `users:disable`. Отдельный ключ входа сайта ещё уже. Существующие ключи не изменялись.

Собранная команда `quota-api check-provider` запущена на сервере сайта с его действующим ключом. Результат:

| Проверка | Результат |
| --- | --- |
| `system:metadata` | Успех, версия 3.4.3 |
| `internal-squads:list` | Успех |
| `profile:main`, `profile:cdn` | Оба UUID найдены |
| `users:by-username`, `users:by-id` | Чтение доступно |
| `subscriptions:connection-keys` | HTTP 403, `missing_api_scope` |

Для проверки записи создан отдельный временный ключ с перечисленными в [развёртывании](deployment.md) правами и дополнительным `users:delete` для уборки теста. Использовались уникальные имена `rqlive_<случайный-id>_main` и `..._cdn`, собственный маркер, срок один час для первоначальной настройки и CDN-квота 1 MiB. Существующие пользователи не изменялись.

Тест `TestLiveRemnawaveBundleLifecycle` прошёл через Go SDK, настоящий HTTP-обработчик объединения и адаптер действующей панели. Проверены:

- Создание двух разных ID пользователей с отдельными лимитами.
- Повтор `PUT` без смены ID и дублирования пользователей.
- Общий URI-список с обеими метками MAIN/CDN.
- Отключение только CDN: его статус в панели стал DISABLED, MAIN остался ACTIVE и сохранился в общей подписке.
- Обратное включение CDN, увеличение его лимита до 2 MiB и продление без изменения срока MAIN.
- Определение аккаунта по общей ссылке для сайта.
- Смена токена: старый URL и его разрешение для входа перестали работать.

Тест использовал временное хранилище в памяти и HTTP listener на loopback. Постоянная база нового сервиса на рабочем сервере не создавалась. Обе тестовые записи удалены, их отсутствие проверено. Временный ключ отозван, загруженные диагностические файлы удалены.

## Что исправлено в проекте

- Разрешены базовые имена до 34 символов при ограничении полного `username_key` до 36. Это совместимо с 29-символьными именами, которые генерирует сайт.
- Добавлены защищённый `POST /api/v1/subscriptions/resolve` и метод SDK `ResolveSubscription` для входа по общей ссылке. URL проверяется по настроенному origin и локальной базе, внешняя загрузка не выполняется.
- Добавлена команда `check-provider`: диагностика чтения и профилей без создания пользователей и подключения к базе.
- Ошибки прав панели выделены в `provider_access_denied`; секреты и сырые ответы панели не попадают в ошибки API.
- Добавлены проверки совместимости и явно включаемый тест реальной панели; обновлены OpenAPI и инструкции интеграции.

## Последовательность подключения сайта

1. Поднять постоянный `quota-api` с отдельной PostgreSQL и отдельным ограниченным API-токеном панели. Удобно разместить его рядом с Go API сайта и обращаться внутри Docker-сети. Вариант на сервере панели также возможен, но потребует защищённого межсерверного маршрута для API.
2. Выбрать публичный origin общей подписки. Можно добавить `/sub/*` к существующему домену, сохранив нативные пути `/{shortUuid}`, либо использовать отдельный домен. Текущий Caddy требует явного маршрута; его конфигурация в этой сессии не менялась.
3. В отдельной копии проекта сайта добавить модель прав по частям, интеграцию worker через SDK, серверную выдачу `parts` и новый вариант сессии по ссылке. Проверять `202` и `sync_status`: принятый запрос ещё не означает завершённую выдачу.
4. Для существующих клиентов сначала определить явные связи с подписками; нативный вход и старые ссылки сохранять до завершения переноса. Новых пользователей создавать с двумя суффиксами и отдельными счётчиками.
5. Проверить VPN-клиентом оба подключения, исчерпание малого лимита CDN, поведение уже открытого соединения и сохранение MAIN. Проверить отображение расхода и отзыв сессии сайта после смены общей ссылки.
6. После проверки переключить выдачу новых подписок на новую интеграцию и наблюдать ошибки синхронизации. Не оставлять два worker/controller, меняющих одни и те же записи панели.

Правила периода остаются у приложения: календарный сброс панели и выдача нового объёма при продлении — разные операции. `quota-api` сохраняет расход при обычном обновлении. Перед интеграцией worker нужно закрепить техническое правило обновления периода, не встраивая цены в этот сервис.

## Границы проверки

Проверены API панели, реальные создаваемые записи, выдаваемые URI и независимые настройки. Реальный VPN-трафик не генерировался; исчерпание квоты, завершение существующих соединений, периодический сброс и отображение новых карточек на рабочем сайте пока не проверены. Проверка PostgreSQL нового сервиса выполнена локально; сайт и его база не мигрировались. Действующие контейнеры и маршруты не переключались.
