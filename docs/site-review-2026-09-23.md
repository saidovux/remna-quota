# Повторная проверка сайта и границы интеграции

23 сентября 2026 повторно обследована действующая установка `/opt/futcinvpn`. Выполнялись чтение исходников, GET health и SQL в транзакции `READ ONLY`. Рабочий сайт и его настройки не менялись.

## Подтверждено

- API/worker работают из образа `futcinvpn-api:20260923-multi-subscriptions`; API, PostgreSQL и SuperTokens здоровы. `/api/health` вернул 200 с успешными проверками авторизации, базы и Remnawave.
- Миграция `00002_multi_subscriptions.sql` применена. Удалены ограничение одной подписки на клиента и поле `customers.remnawave_user_id`; связь с панелью находится у отдельной подписки.
- Код новой покупки создаёт отдельную запись подписки. Продление требует авторизованного пользователя и проверяет выбранную подписку вместе с её владельцем.
- Обработчик webhook использует транзакцию, уникальную запись события, блокировку заказа и проверку уже оплаченного состояния перед повторной выдачей.
- Worker передаёт `SubscriptionID`; имя Remnawave теперь строится от ID подписки, а не клиента. При продлении используется ID её пользователя панели.
- Платёжный провайдер по текущей конфигурации выключен. В базе на момент чтения 2 клиента и 0 подписок.

Заявленные пользователем 16 production E2E и сценарии mock-оплаты в этой проверке повторно не запускались; выводы выше основаны на действующем коде, схеме и health.

## Что это означает для remna-quota

Предыдущий отчёт [обследования](live-assessment-2026-09-23.md) зафиксировал состояние до обновления сайта. Его вывод об одной подписке на клиента больше не актуален. Новая модель позволяет связать **отдельный набор** объединения с отдельной записью подписки приложения.

Основной API теперь оперирует `bundles` и существующими `sources`. Приложение передаёт ID исходных пользователей Remnawave, а сервис читает их без изменения username, description, квот и сквадов. Для сайта и бота используются одинаковые API, SDK и переменные подключения; предметных правил FutcinVPN в основном сервисе нет.

Конструктор интерфейса выбирает обычный доступ и CDN. В обследованном серверном provisioning-коде один `Plan.Squad` по-прежнему выбирает один сквад для одной исходной подписки. Чтобы получить два независимых счётчика в конструкторе, вызывающее приложение должно передать набору две существующие независимые исходные подписки. Добавить две метки к одному пользователю недостаточно. Выдача этих исходных подписок остаётся ответственностью приложения или отдельно включённого технического provisioning API.

При обновлении существующего пользователя код сайта всё ещё вызывает `reset-traffic`. Это отдельное поведение выдачи/продления сайта; объединитель его не вызывает и не исправляет. Идемпотентность webhook сама по себе не означает, что повтор прерванного worker-задания не повторит этот сброс.

## Контракт будущего подключения

1. Сайт или бот проверяет владельца и создаёт/продлевает исходные подписки своим штатным механизмом.
2. Приложение сохраняет стабильный ID набора для конкретной подписки/композиции. Несколько наборов могут иметь одинаковый `external_ref` владельца.
3. `PUT /api/v1/bundles/{id}` передаёт массив источников. Повтор одного события использует тот же ID. Конструктор может использовать атомарные PUT/DELETE отдельного источника.
4. Общую ссылку приложение получает из ответа, а карточки — из `sources` после refresh. Данные покупки и авторизации в remna-quota не передаются.
5. Для конфликтующих изменений используется `expected_revision`. Удаление набора или источника никогда не удаляет исходную подписку панели.

Подключение рабочего сайта и публикация общей ссылки в этой сессии не выполнялись. Реализован и проверяется общий контракт, пригодный для любого доверенного приложения.
