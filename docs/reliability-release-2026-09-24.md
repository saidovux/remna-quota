# Исправления надёжности remna-quota — 24 сентября 2026

Обновлены код, API, Go SDK и документация. Версия установлена на существующий экземпляр `quota-test` в `/opt/remna-quota-test`. Работа выполнялась только над remna-quota; Xray, Remnawave и ноды не патчились.

## Исправлено

- Перерасход больше не повышает нативный лимит. Повторная синхронизация не включает исчерпанного пользователя и не пополняет его пакет.
- Учёт `NO_RESET` использует накопительный счётчик панели. Повторные снимки не списываются дважды; необъяснимое уменьшение счётчика сохраняет прежние списания и выставляет `accounting_status: anomaly`. Сбросы и пересоздание не дают новую квоту. Первый снимок после потерянного ответа создания также учитывает накопительный расход; старые записи сохраняют прежний учёт.
- Убраны сетевые вызовы из транзакций PostgreSQL, в том числе в дополнительном API объединения существующих подписок. Успешные наблюдения сохраняются независимо от последующих ошибок. Запоздавшие чтения не затирают новые данные.
- Операции одного аккаунта сериализуются отдельной блокировкой между репликами. Старый ответ панели не подтверждает новую revision и останавливает дальнейшие изменения по старой конфигурации.
- Фоновый диспетчер использует до четырёх рабочих слотов и сохранённое расписание. Медленный аккаунт не задерживает повторные запуски остальных. Ошибки откладывают повторы до пяти минут; более длинный `Retry-After` имеет приоритет и переживает перезапуск.
- HTTP-запрос ждёт до пяти секунд, затем получает `202`. Отмена запроса не отменяет сохранённую работу. Чтение списка не ждёт панели. Остановка сервиса завершает фоновые задачи.
- Добавлены защищённые `/api/v1/diagnostics`, `/api/v1/metrics`, поля `observed_at`, `applied_revision`, `accounting_status`, `next_retry_at`, `last_attempt_at`, `failure_count`. Обновлены OpenAPI и Go SDK. Неподтверждённая общая подписка возвращает `503`.

Проверены отмена запроса, смена revision во время ответа панели, частичные наблюдения, четыре рабочих слота, задержки, `429`/`503`, `Retry-After`, ротация ссылки во время чтения и отсутствие доступа к диагностике без ключа.

## Что остаётся вне remna-quota

1. **Устранено настройкой панели 24 сентября в 21:06 МСК.** По поручению владельца для MAIN (Frankfurt) изменён `consumptionMultiplier` с `0` на `1` через штатный `PATCH /api/nodes`. Повторное чтение подтвердило значение `1` и подключённое состояние ноды. Лимиты Oleg сохранены: MAIN 100 000 000 байт, CDN 50 000 000 байт; расход CDN не сбрасывался. Остальные настройки ноды проверены на неизменность. Теперь дальнейший трафик через MAIN учитывается с обычным коэффициентом; индивидуальный безлимит задаётся нулевым лимитом пользователя. Состояние в таблице выше относится к проверке до этого изменения.
2. В установленной Xray отключение пользователя VLESS не гарантирует закрытие уже открытого потока. Реальный CDN-тест показал продолжение загрузки после статуса `DISABLED`. Это отдельное ограничение, а не только небольшой перерасход из-за периодического сбора статистики. remna-quota не может точно закрыть такой поток через доступный стандартный API.

Подробности реального трафикового теста — в [отчёте исследования квот](quota-investigation-2026-09-24.md). Никакого собственного измерителя VPN-трафика, патчей Xray или автоматического уничтожения соединений по IP в remna-quota нет. Сайт, платежи и фронтенд в этом обновлении не менялись.
