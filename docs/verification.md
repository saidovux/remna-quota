# Проверки и текущие ограничения

Обновлено 24 сентября 2026 года. Основной режим создаёт пользователей Remnawave, синхронизирует независимые квоты и выдаёт объединённые подписки. Режим объединения существующих записей сохранён как дополнительный API bundles. Итог текущего выпуска и серверная проверка — в [отчёте надёжности](reliability-release-2026-09-24.md).

## Выполнено для текущей версии

- Go 1.27.1: `go test ./...` с настоящей локальной PostgreSQL 18.4 проходит. Проверено обновление с миграции 4 до `00005_sync_schedule.sql` с сохранением истории расхода и ссылки. Также проверены отдельная блокировка операций между репликами, запись новых настроек во время блокировки, долговечность повторов, откат, уникальность username и выборка по фильтрам и курсору.
- На Linux успешно завершены `go test -p 1 -race ./...`, `go vet ./...` и сборка контейнера штатным Dockerfile. Новые тесты покрывают накопительный счётчик, устаревшие показания, `Retry-After`, отмену HTTP-запроса, ожидание до пяти секунд, четыре рабочих слота, запоздавшие ответы и смену revision. Диагностика и новые поля проверены через HTTP и Go SDK.
- `TestCounterResetPreservesPackageAndCDNExhaustionKeepsMain`: конечная квота MAIN 200 GiB и CDN 70 GiB; наблюдение 37 GiB, сброс панели и новые 5 GiB дают логические 42 GiB. После 70 GiB CDN отключён, MAIN работает. Повторные чтения не удваивают расход; сброс исчерпанного счётчика не превращает нативный лимит в безлимит. Увеличение до 100 GiB возвращает только 30 GiB.
- `TestTrafficResetTimestampRecreationAndPeriodicCycles`: обнаружение сброса по timestamp даже при новом счётчике больше предыдущего, смена ID пользователя, различие NO_RESET и периодического учёта.
- `TestEnsureNativeBudgetAfterCounterResetAndRecreation`: HTTP-имитатор Remnawave подтверждает передачу оставшейся квоты после сброса/пересоздания и отключение при нулевом остатке. Неожиданные upstream-методы отклоняются, сброс счётчика адаптер не вызывает.
- `TestManagedDirectoryAndIndependentPartUpdates`: Go SDK → HTTP API → сервис → хранилище → demo. Проверены capabilities с профилями, несколько подписок на один external_ref, страницы списка, добавление CDN, конфликт revision, независимое отключение и отключение всего аккаунта.
- `TestConcurrentPartUpdatesPreserveBothConfigurations`: одновременные изменения MAIN/CDN сохраняют обе конфигурации; чтение трафика не изменяет revision и updated_at настроек.
- Сохранены проверки идемпотентности, частичных сбоев, повторной синхронизации, строгого JSON, обязательного явного лимита, авторизации, no-store, ротации токена, устаревших показателей и сохранения расхода при продлении.
- `go vet ./...`, `go build ./...` проходят. Собраны `bin/quota-api.exe` и `bin/quota-api-linux-amd64`; это локальные артефакты, каталог исключён из Git.
- YAML Compose, CI, основной OpenAPI и дополнительный контракт разобраны парсером; внутренние `$ref` проверены. Это не полная семантическая проверка OpenAPI.

## Действующая панель

23 сентября на предоставленной Remnawave 3.4.3 выполнен `TestLiveRemnawaveBundleLifecycle`. С отдельным временным API-ключом созданы только два временных пользователя с уникальными именами и точными маркерами принадлежности.

Проверены создание MAIN/CDN, повтор без дублей, общий список подключений, список управляемых аккаунтов, новые поля статистики, отдельное отключение/включение CDN, изменение его квоты и срока, resolver и отзыв общей ссылки. Тест завершился успешно. Удаление временных пользователей подтверждено; временный ключ отозван, исполняемый файл удалён.

Этот тест использовал память и локальный HTTP listener. 24 сентября отдельно проверен реальный CDN-трафик: обнаружено продолжение уже открытого потока после отключения пользователя. Ноды не патчились; результаты приведены в [исследовании квот](quota-investigation-2026-09-24.md).

Постоянный экземпляр `quota-test`, собственная PostgreSQL и публичный маршрут развёрнуты. После обновления проверены сохранность ссылки тестовый аккаунт, ID пользователей, расхода CDN и нативного лимита; ссылка отдаёт MAIN без исчерпанного CDN. Резервная копия сделана до обновления.

Ранее выполнен также `TestLiveReadOnlyAggregation`: два существующих источника, временный ключ только для чтения, transport с запретом записи. Исходные пользователи не менялись. Его результаты относятся к дополнительному API bundles, а не к управлению пользователями.

## Что остаётся проверить при вводе в эксплуатацию

- Поведение выбранных пользователем VPN-клиентов после обновления подписки. Закрытие уже открытых VLESS-потоков установленная Xray не гарантирует; remna-quota не патчит ядро и не уничтожает чужие соединения по IP.
- 24 сентября в 21:06 МСК по поручению владельца коэффициент пользовательского расхода MAIN изменён с `0` на `1` через API панели. Значение повторно прочитано; MAIN тестовый аккаунт сохраняет лимит 100 MB, CDN — 50 MB и ранее списанный расход. Реальную загрузку через MAIN после этого изменения в рамках данной проверки не запускали.
- Проверки Linux/race/контейнера выполнены на сервере в отдельном тестовом окружении. GitHub CI из этой сессии не запускался; полный сценарий установки Compose на чистом сервере отдельно не проверялся.
- Старый integration-тест Bedolaga пропускается без его отдельной legacy-конфигурации. Новый репозиторий PostgreSQL проверен на реальной базе.
- Сайт/бот к новому API не подключены; их рабочий код не менялся. Автоматического переноса существующих пользователей и ссылок пока нет.
- Накопительный счётчик позволяет учесть трафик между сбросами, пока запись и сам счётчик сохранены. Неизвестный расход удалённого пользователя восстановить нельзя. Подробности — [учёт трафика](traffic-accounting.md).
