# Дополнительная установка только для объединения существующих подписок

Основная установка создаёт и синхронизирует пользователей; она описана в [deployment.md](deployment.md). Здесь управление пользователями явно выключается.

## Доступ к панели

Нужна Remnawave v3 с `GET /api/users/{id}` и `GET /api/subscriptions/connection-keys/{id}`. Создайте отдельный токен с правами:

- `users:by-id`;
- `subscriptions:connection-keys`;
- `system:metadata` для диагностической команды.

Объединение использует только GET. Ему не нужны права создания, изменения, удаления или сброса трафика. В API набора указываются реальные ID уже существующих пользователей. Принадлежность этих подписок конечному пользователю проверяет вызывающее приложение.

## Docker Compose

```bash
cp .env.example .env
chmod 600 .env
```

Сгенерируйте два независимых ключа командой `go run ./cmd/quota-api keygen` либо `openssl rand -hex 32`. Сохраните их в `BACKEND_API_KEY` и `QUOTA_DB_PASSWORD`.

```dotenv
BACKEND_PROVIDER=remnawave
BACKEND_ENABLE_MANAGED_ACCOUNTS=false
BACKEND_PUBLIC_URL=https://subscriptions.example
BACKEND_API_KEY=
QUOTA_DB_PASSWORD=
REMNAWAVE_BASE_URL=https://panel.example
REMNAWAVE_API_TOKEN=
REMNAWAVE_PROFILES_JSON='{}'
```

Compose сам формирует строку подключения к своей базе. Пароль должен быть безопасен для URL; указанные генераторы подходят.

```bash
docker compose config --services
docker compose build
docker compose run --rm --no-deps quota-api check-config
docker compose run --rm --no-deps quota-api check-provider
docker compose up -d
curl --fail http://127.0.0.1:8090/readyz
```

Порт HTTP публикуется только на `127.0.0.1:8090`, порт PostgreSQL не публикуется. Данные находятся в отдельном томе `quota-api-postgres`. При старте применяются миграции, включая таблицу `subscription_bundles`; базы панели, сайта и бота не используются.

Без Docker задайте `BACKEND_DATABASE_URL` на собственную PostgreSQL и запустите `quota-api`. Для соединения с БД через публичную сеть используйте проверяемый TLS. В demo собственная база не нужна и данные не сохраняются после остановки.

## Диагностика

`check-config` проверяет синтаксис настроек. `check-provider` делает GET-запросы к панели, проверяя версию и маршруты чтения пользователей/connection keys. Он не открывает базу, хотя обычные параметры `BACKEND_API_KEY` и синтаксически корректный `BACKEND_DATABASE_URL` обязательны.

Результат — JSON с `read_checks_passed`, `version`, `checks`, `write_scopes_verified: false`. Неуспех возвращает код завершения 1. `missing_api_scope` соответствует HTTP 403, `invalid_api_token` — 401; запрет также может исходить от прокси. Пробные несуществующие ID и допустимый 404 проверяют доступ к маршруту, но не доказывают работоспособность конкретной подписки. После запуска проверьте действительные источники через `GET /api/v1/bundles/{id}?refresh=true` и загрузку общей ссылки.

`/readyz` проверяет только собственное хранилище. Ошибки источников видны в `sources[].last_error` и `stale`; `readyz` не обещает доступность панели.

Для доверенной Docker-сети доступны `REMNAWAVE_ALLOW_HTTP=true` и параметры `REMNAWAVE_FORWARDED_FOR`, `REMNAWAVE_FORWARDED_PROTO`, `REMNAWAVE_CADDY_API_KEY`, если их требует прокси панели. По умолчанию требуется HTTPS.

## Публичная ссылка и серверный API

На публичном домене публикуйте `/sub/*` через HTTPS. API интеграторов доступен по приватной сети или отдельному защищённому HTTPS-маршруту с серверным Bearer-ключом. Не передавайте его браузеру.

Пример Nginx внутри TLS server block:

```nginx
location /sub/ {
    access_log off;
    proxy_pass http://127.0.0.1:8090;
    proxy_read_timeout 120s;
    proxy_cache off;
}
```

Пример Caddy, если proxy и API находятся в одной Docker-сети:

```caddyfile
subscriptions.example {
    handle /sub/* {
        reverse_proxy quota-api:8090
    }
    handle {
        respond 404
    }
}
```

Если домен уже обслуживает нативные подписки, сохраните их маршруты `/{shortUuid}` и добавьте только `/sub/*`. Не используйте `handle_path`, отрезающий префикс, который нужен API. Не направляйте контейнерный proxy на `127.0.0.1` другого контейнера; настройте общую Docker-сеть и имя сервиса.

Исключите `/sub/*` и `/api/*` из CDN-кэширования и журналирования полных URL/тел запросов. Токен общей ссылки — секрет. На внешнем proxy задайте ограничения частоты запросов; каждая загрузка читает панель. Внутри одного набора одновременно читаются до четырёх источников, операции над набором сериализованы.

## Проверка выдачи

1. Прочитайте capabilities, создайте отдельный набор из известных тестовых подписок.
2. Убедитесь в отдельных счётчиках через refresh и метках подключений в plain/Base64.
3. Исключите CDN из набора: MAIN должен остаться; пользователь CDN в панели не должен измениться.
4. Измените срок/квоту тестовой исходной подписки её штатным механизмом и проверьте новые наблюдения без пересоздания набора.
5. Проверьте конфликт `expected_revision`, сохранение токена после перезапуска, отзыв токена и удаление набора.
6. VPN-клиентом проверьте подключения и фактическое ограничение CDN на нодах. Объединитель не заменяет нативное применение квот панелью.

## Резервная копия и обновление

```bash
docker compose exec -T quota-postgres pg_dump -U quota -d quota -Fc > quota-backup.dump
```

Дамп содержит секретные ссылки и должен храниться с ограниченным доступом. Перед обновлением создайте резервную копию. Не используйте `docker compose down -v`, если нужно сохранить ссылки. Для восстановления остановите API и восстановите дамп в отдельную проверенную базу, затем запустите сервис.

## Предыдущая модель accounts

При явной настройке `BACKEND_ENABLE_MANAGED_ACCOUNTS=false`: маршруты `/api/v1/accounts/*`, прежний resolver и фоновое изменение пользователей выключены. Сохранённые записи `account_bundles` не удаляются, но их общие ссылки не обслуживаются без включения managed-режима. При обновлении уже работающей предыдущей установки сохраните `BACKEND_ENABLE_MANAGED_ACCOUNTS=true` до явного перехода.

Для этого режима дополнительно нужны профили сквадов и права записи. [Настройка основного режима](deployment.md), [API](integration.md). Наборы `subscription_bundles` и управляемые accounts — разные ресурсы; автоматического переноса нет. В режиме только объединения нельзя считать старый provisioning worker активным источником продлений.
